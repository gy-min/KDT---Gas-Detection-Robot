# 프로젝트 배경

가스 감지 로봇/센서 시스템의 **직원용 Android 앱**입니다. 6명이서 한 달 안에 만드는
초단기 소규모 프로젝트의 일부입니다.

## 전체 시스템 개요

1. 가스 센서(로봇 + 고정 센서)가 가스를 감지합니다.
2. 서버가 감지값을 시계열로 분석해 결론(가스 종류, 위험도 등)을 내고 DB에 저장합니다.
3. 서버는 이 정보를 실시간으로 이 앱과 관리자 웹(별도 프로젝트)에 계속 흘려보내고,
   앱/웹은 그걸 받아 화면을 갱신하고 필요하면 행동(경보 등)을 취합니다.

## 내 담당 범위

이 저장소(Android 앱)만 담당합니다. FastAPI 서버와 관리자 웹은 다른 팀원이 만들고
있고, 저는 그쪽 코드를 직접 수정하지 않습니다. **팀원이 서버/웹을 바꿀 때마다 그
코드를 전달받아서, 이 앱을 거기에 맞춰 다시 업데이트하는 식으로 작업이 진행됩니다.**
서버 API 계약은 [BACKEND_API.md](BACKEND_API.md)에 정리되어 있고, 서버가 바뀌면 이
문서도 같이 갱신합니다.

## 코드 작성 원칙 (중요)

**한 달짜리, 6명 규모 프로젝트입니다. 복잡하거나 과한 설계는 오히려 방해가 됩니다.**

- 단순하고 직관적인 구조를 최우선으로 합니다. 나중에 확장될지도 모른다는 이유로
  미리 추상화 계층을 만들지 마세요.
- DI 프레임워크(Hilt/Dagger/Koin 등), 불필요한 인터페이스, 싱글 구현체뿐인
  추상 클래스는 쓰지 않습니다. 지금처럼 수동으로 조립하는 정도(companion object
  싱글턴, 생성자 주입)면 충분합니다.
- 실제로 일어날 수 없는 상황에 대한 방어 코드(과도한 null 체크, 안 쓰이는
  에러 핸들링, 동시성 걱정이 없는 곳의 synchronized/@Volatile)는 넣지 않습니다.
- 코드 3줄이 비슷하게 반복되는 정도는 괜찮습니다. 억지로 공통 함수로 뽑아내다가
  오히려 읽기 어려워지면 그게 더 나쁩니다. 다만 완전히 동일한 로직이 여러 곳에
  복붙되어 있다면(예: 기기 버전별 시스템 서비스 가져오기 같은 보일러플레이트)
  작은 헬퍼 함수 하나로 묶는 정도는 괜찮습니다.
- 주석은 "왜 이렇게 했는지"가 코드만 봐서는 안 보일 때만 답니다. 코드가 이미
  하는 일을 그대로 설명하는 주석은 쓰지 않습니다.

## 아키텍처 (현재 구조, 그대로 유지)

```
MonitoringRepository (서버와 통신하는 단일 소스)
        ↓ StateFlow
MonitoringViewModel
        ↓ uiState
Compose 화면 (ui/screens/*.kt)
```

- `MonitoringRepository` — REST(초기 로딩/폴백) + WebSocket(실시간)을 합쳐서
  하나의 `MonitoringSnapshot`으로 만들어 흘려보내는 유일한 지점. 화면은 이걸
  절대 직접 건드리지 않고 ViewModel을 통해서만 봅니다.
- `MonitoringForegroundService` — 앱이 백그라운드여도 서버 연결을 유지하고,
  위험 상황이면 알람(사이렌/진동/전체화면)을 직접 트리거합니다.
- 화면은 3개뿐입니다: 홈(상태 요약) / 대피 경로(구역 지도) / 119 신고.

## 알려진 제약

- 이 개발 환경(샌드박스)에서는 `./gradlew` 빌드가 항상
  `Unable to establish loopback connection` 오류로 실패합니다. 환경 문제이지
  코드 문제가 아닙니다 — 빌드 확인이 필요하면 실제 기기/에뮬레이터가 있는
  환경에서 직접 돌려봐야 합니다. 코드 리뷰로 최대한 검증하고, 확인이 안 됐다는
  점을 명시적으로 알려주세요.
- 서버(`evacuation.py` 등)가 앱보다 늦게 업데이트되는 경우가 많습니다. 앱 쪽
  UI/데이터 구조가 서버의 실제 스키마보다 앞서갈 때는, 억지로 우회 코드를 짜지
  말고 그 사실을 코드 주석이나 UI 문구로 남겨서 나중에 서버가 따라오면 바로
  맞춰볼 수 있게 해두세요.
